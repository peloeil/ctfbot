# 設計の引き継ぎ

Codex が期待する振る舞いと完了条件を判断できる設計を残す。通常の修正や文書編集に、この引き継ぎを挟む必要はない。

関連する実装・テスト・仕様を確認し、変更の目的、入出力、必要な制約、受け入れ条件をまとめる。認可・公開範囲・上限・状態遷移・競合・失敗時の補償は、その機能に関係するものを記す。厳密な文言や操作順序は、それ自体が要件の場合に指定する。

## 保存先

- 継続して参照する振る舞いは `docs/features/{feature-name}.md` に置く。新しい機能は `README.md` の機能一覧からリンクする。
- 設定・永続化の契約は `docs/data-contracts.md`、共有する設計理由は `docs/design.md` を必要に応じて更新する。型宣言・SQL・既存文面の全文は実装を参照し、複製しない。
- 短い引き継ぎは、変更理由・作業範囲・受け入れ条件と関連仕様へのリンクを会話内にまとめる。段階的な移行や長い設計など、別途参照する文書が必要な場合は `docs/tasks/YYYY-MM-DD-{name}.md` に保存する。未決事項を区別し、具体的なコードや対象ファイルの網羅列挙は必要な場合だけ含める。

共通ルールは [AGENTS.md](../../../AGENTS.md) を参照する。段階化は独立した検証・移行が必要な場合に行う。依頼されていない承認待ちや固定の実装順を増やさない。

設計と実装待ちの状態を区別し、未実装の変更を既存機能として記載しない。実装完了後は必要な契約・判断理由を恒久文書に残し、役目を終えたタスク文書を削除する。

## 引き継ぎ

ユーザーがそのまま渡せる短い依頼文を返す。タスク文書を作成した場合はその文書を指定し、作成しない場合は依頼文に作業範囲と受け入れ条件を含める。実装・関連文書の更新・検証までを完了範囲にする。共通ルールを再掲しない。
